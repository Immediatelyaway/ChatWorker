# ADR-0001：存储边界与 SQLite 驱动选择

日期：2026-10-22 · 对应任务：CW-002 · 状态：驱动选型通过，业务迁移待 CW-003。

## 问题与决策

现有 `Storage` 同时负责文件读写、数据校验和中断消息恢复。直接把 JSON 调用替换成 SQL，会把存储选型、业务迁移和恢复规则混在一次变更中。

本次先引入 `SnapshotRepository<T>`，由 `JsonSnapshotRepository` 实现现有全量快照的读写。应用层继续校验格式、恢复中断消息和创建初始状态。选择 Node 内置的 `node:sqlite` 作为下一阶段 SQLite 驱动，提供独立连接入口，并用相同检查验证 Node、Electron 主进程及打包后的 Electron 应用。

| 候选                    | 本次结论                                                                               |
| ----------------------- | -------------------------------------------------------------------------------------- |
| 继续使用 JSON           | 保留为当前生产路径和迁移前来源；无法满足后续关系事务、分页和事件存储需求               |
| 内置 `node:sqlite`      | 当前运行时已自带，实际读写及桌面打包试验通过；无需新增第三方原生扩展，作为后续迁移首选 |
| 外置 SQLite 驱动 / WASM | 本次未安装、未跑性能对比；若运行时兼容或性能不达标再单独验证，不据此宣称内置驱动更快   |

**当前应用仍写 `state.json`，能力接口仍报告 `json-file`，没有创建业务数据库或自动迁移用户数据。**

## 代码边界

| 文件                                           | 责任                                                                        |
| ---------------------------------------------- | --------------------------------------------------------------------------- |
| `packages/storage/snapshot-repository.ts`      | 过渡期全状态接口：`load()` 返回未知数据或不存在，`save()` 失败向上传递      |
| `packages/storage/json-snapshot-repository.ts` | JSON 解析、临时文件写入与原子替换；不重置损坏文件，不判断业务格式版本       |
| `apps/server/src/storage.ts`                   | 选择默认 JSON 实现、调用 schema 校验、修复旧 streaming 状态、保存与替换状态 |
| `packages/storage/sqlite.ts`                   | 候选连接入口、日志模式、外键、同步设置、等待上限及 WAL 版本检查             |
| `tests/helpers/sqlite-contract.ts`             | 在三个运行环境复用的事务与持久化验收，测试表不是未来业务表结构              |
| `scripts/verify-storage.mjs`                   | 编译试验、运行 Node/Electron、生成隔离的桌面测试应用并执行                  |

JSON 实现没有长驻连接，不需要伪造关闭操作；SQLite 调用者必须在 `finally` 中关闭连接。应用不直接导入 SQLite 入口，因而当前聊天服务不会加载试验模块。后续关系仓储应按项目、会话、消息等操作提供事务边界，不应把整个 `State` 永久塞成数据库里的一个 JSON 字段。

`Storage.replace()` 仍先保存后替换内存，失败时原状态不变。部分现有路由仍采用“先改内存再 save”的方式，本次重构没有把这些路由变成事务；CW-003 必须处理持久化失败后的内存一致性。

## 连接规则与 WAL 选择

入口只接受绝对路径，目录由调用者创建并管理。试验使用独立私有临时目录；数据库创建权限为 `0600`，macOS 检查日志文件权限同样为 `0600`。这不是 Windows ACL 验收，也不是任意路径或符号链接访问授权机制。

默认使用 `journal_mode=DELETE`、`synchronous=FULL`、外键开启、扩展加载关闭和双引号字符串关闭。等待写入锁默认上限为 1000ms，可配置 0–30000ms；配置错误先拒绝，不创建文件。设置后读取 PRAGMA 实际结果，不只依赖设置语句未报错。[SQLite PRAGMA 说明](https://sqlite.org/pragma.html)

没有默认采用 WAL，是因为本机 Node 22.21.1 内置 SQLite 3.50.4。SQLite 官方披露的 WAL-reset 问题涉及多连接在不同线程或进程中并发写入/检查点，修复版本为 3.51.3 及以后，并有 3.44.6、3.50.7 回移修复。入口按实际引擎版本检查，旧版本明确拒绝 WAL，不静默退回其他模式；版本检查不代表对未来所有缺陷的保证。[SQLite WAL-reset 说明](https://sqlite.org/wal.html#walresetbug)

Electron 的实际引擎为 3.53.4，本次同时验证 DELETE 与 WAL。WAL 可以作为以后经测量选择的显式模式；其检查点、备份和本地文件系统要求仍需由业务仓储管理。[SQLite WAL 文档](https://sqlite.org/wal.html)

## 验证方法与结果

运行 `npm test` 和 `npm run verify:storage`。试验以本机 Node 22.21.1 为基线，依赖已安装的 Electron 和 electron-builder；首次依赖安装可能需要网络。试验进程不打开聊天窗口、不调用真实模型、不读写 ChatWorker 用户目录，结束后删除临时数据库和测试应用。

| 环境（macOS arm64）          | Node    | SQLite | DELETE | WAL                               |
| ---------------------------- | ------- | ------ | ------ | --------------------------------- |
| 本机 Node                    | 22.21.1 | 3.50.4 | 通过   | 按版本保护拒绝，未创建 WAL 数据库 |
| Electron 44.9.0 主进程       | 24.22.0 | 3.53.4 | 通过   | 通过                              |
| Electron 44.9.0 打包测试应用 | 24.22.0 | 3.53.4 | 通过   | 通过                              |

相同检查覆盖：中文/表情/换行与包含 SQL 符号的绑定参数往返、二进制内容、跨表提交、约束失败后的整笔回滚、外键、重复 ID、第二连接读取已提交状态、第二写入者收到 `SQLITE_BUSY`、锁释放后可再次提交、关闭重开、数据库快速完整性检查。单元测试另外覆盖无效参数、损坏文件字节不被覆盖、旧版/未来版 JSON 和持久化失败。

打包脚本使用真实 electron-builder `--dir` 产出应用，从应用自己的可执行文件启动，断言 `process.type=browser`、`app.isPackaged=true` 且代码位于 `app.asar`。数据库位于归档外的临时目录；ASAR 是只读归档，不能放运行时数据库。[Electron ASAR 文档](https://www.electronjs.org/docs/latest/tutorial/asar-archives)

这项验收是最小存储测试应用的打包运行，不是整套 ChatWorker 窗口、安装程序、公证或自动更新验收。未验证 Windows/Linux、跨进程争用、强制断电、磁盘故障和长时间压力负载。当前锁冲突试验使用同一进程的两个连接，不能证明跨进程唯一服务实例已经实现。

## 代价与实施约束

`node:sqlite` 在 Node 22.21.1 文档中仍标为开发中的 API，运行时会提示实验性；同步接口及等待锁会阻塞调用线程。因此不能在渲染进程导入它，也不能把长查询放入未来的高频生成路径。CW-003 接入前需验证持久化工作线程/服务隔离或有证据的短事务上限，并实现退出时先等待写入结束再关闭连接。[Node 22.21.1 SQLite 文档](https://nodejs.org/download/release/v22.21.1/docs/api/sqlite.html)

本次试验不引入 schema 迁移，不增加 ORM，不变更应用/备份版本。默认回滚日志的并发与吞吐尚未做量化比较；`FULL` 设置也不构成所有硬件故障下永不丢失数据的保证。SQLite 驱动属于连接层，不负责识别任意已有文件中的 ChatWorker schema；未来的仓储必须先校验版本，再调用可写入口。

## CW-003 的具体进入与验收条件

1. 确定业务表与迁移版本，建立稳定 `storeId`；版本独立于应用版本和 v1 备份格式。SQLite 仓储读模型继续适配现有 API。
2. 先获得资料目录唯一写入权，再只读校验旧 JSON、已有数据库版本及日志状态；拒绝损坏或未知未来版本，不覆盖、不隐式初始化为空库。旧程序仍运行时不能迁移。
3. 将旧 JSON 复制到独立迁移备份并核验 SHA-256。新数据库写入临时位置，用事务保留 ID、消息顺序、附件、归档、项目关联及原活动文字；旧 streaming 转为中断历史。
4. 校验计数、引用和内容后关闭并持久化数据库，再原子切换。不得长期双写 JSON/SQLite。针对“备份后、导入中、提交后、切换前、切换后”分别模拟进程中断，重启时识别阶段并安全继续或退出。
5. 旧 JSON 和迁移备份不自动删除。新库开始接受修改后，禁止自动回退到旧 JSON 丢失新内容；人工回退必须说明恢复点。以后若采用 WAL，不可只复制正在写入的主库文件充当备份。
6. 测试磁盘写入失败、重复启动、关闭连接与活动请求竞态、接口错误返回及内存回滚。完成迁移验收后才修改能力接口的保存方式，随后进入 CW-004 服务端草稿与 revision。

若内置驱动的同步阻塞或版本支持不能满足验收，再重新评估驱动及进程结构；本轮尚未切换生产存储，回退只需撤销试验代码，无需转换用户数据。
